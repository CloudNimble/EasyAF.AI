`McpEssentials.EntityFrameworkCore` is the first durable authenticated task store. It subclasses [`McpTaskStoreBase`](/mcpessentials/api-reference/CloudNimble/McpEssentials/Core/Tasks/McpTaskStoreBase) and persists [`McpTaskEntity`](/mcpessentials/api-reference/CloudNimble/McpEssentials/EntityFrameworkCore/Tasks/McpTaskEntity) rows through **your** `DbContext`.

<CardGroup cols={3}>
  <Card title="Any EF provider" icon="database">
    SQL Server, SQLite, PostgreSQL, MySQL, MariaDB, Cosmos via EF, Oracle — whatever you already pass to `AddDbContext`.
  </Card>
  <Card title="Host owns the model" icon="table">
    Your context, your connection, your migrations. The store opens a scope per operation.
  </Card>
  <Card title="Optional bus" icon="tower-broadcast">
    Multi-node `ElicitAsync` takes [`IMcpTaskInputSignalBus`](/mcpessentials/api-reference/CloudNimble/McpEssentials/Core/Tasks/IMcpTaskInputSignalBus).
  </Card>
</CardGroup>

<Note>
This package works with **any EF Core database provider**. The store talks to `TContext.Set<McpTaskEntity>()`; it never binds a specific engine.
</Note>

The host owns the context, the connection, and migrations. This package ships the entity, [`AddMcpTasksTable`](/mcpessentials/api-reference/Microsoft/EntityFrameworkCore/ModelBuilder) on `ModelBuilder` and on [`DbContextOptionsBuilder`](/mcpessentials/api-reference/Microsoft/EntityFrameworkCore/DbContextOptionsBuilder), and a singleton store that opens a scope per operation so a standard scoped `AddDbContext` works.

## Install

```bash
dotnet add package McpEssentials.EntityFrameworkCore
```

Register an EF Core provider on the context the way you already do:

<CodeGroup>

```csharp UseSqlServer
builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlServer(connectionString));
```

```csharp UseSqlite
builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlite("Data Source=app.db"));
```

```csharp UseNpgsql
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(connectionString));
```

```csharp UseCosmos
builder.Services.AddDbContext<AppDbContext>(o => o.UseCosmos(accountEndpoint, accountKey, databaseName));
```

```csharp UseMySql
builder.Services.AddDbContext<AppDbContext>(o => o.UseMySql(connectionString, serverVersion));
```

</CodeGroup>

## Map the table

Keep MCP task rows on their own table; they expire in minutes. The default name is `McpTasks`. Pass a name and schema on either call to change it: `AddMcpTasksTable("AppTasks", "mcp")`.

The store talks to `TContext.Set<McpTaskEntity>()`. The host does not need a `DbSet`. Both options use the **same** host `DbContext`. Pick **one**.

<Tabs>
  <Tab title="OnModelCreating" icon="code">
    Use this in a single-project app, or whenever the project that owns `AppDbContext` already references this package. Mapping lives with the rest of the model. Migrations from that project see the table.

    ```csharp
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.AddMcpTasksTable();
    }
    ```
  </Tab>
  <Tab title="AddDbContext" icon="puzzle-piece">
    Use this when `AppDbContext` lives in a class library that must stay free of MCP. Only the application project takes this package. Call `AddMcpTasksTable` on the options next to `UseSqlServer` (or whatever provider you already use). EF still uses the same host `DbContext`; the mapping runs after `OnModelCreating`.

    ```csharp
    builder.Services.AddDbContext<AppDbContext>(o =>
    {
        o.UseSqlServer(connectionString);
        o.AddMcpTasksTable();
    });
    ```

    Run migrations with the application as the startup project so the options hook is in the model:

    ```bash
    dotnet ef migrations add AddMcpTasks --startup-project path/to/App
    ```

    <Warning>
    A migration from the context project alone will not see `McpTasks` and can emit a drop.
    </Warning>
  </Tab>
</Tabs>

Mapped columns include `TaskId`, `OwnerUserId`, `Status` (enum name as string), timestamps, `TimeToLive`, `ExpiresAt`, `DiscardAfter` (UTC ticks so every provider, including SQLite, can `ExecuteDelete`), JSON payloads, and an application-managed `RowVersion`. Indexes cover owner, `(OwnerUserId, TaskId)`, `ExpiresAt`, and `DiscardAfter`. SQL Server hosts may remap `RowVersion` as `rowversion` in their own configuration.

## Wire the store

Same identity factory as [Authenticated tasks](/mcpessentials/guides/authenticated-tasks). The SDK `WithTasks` API captures the store before `Build()`; [`WithTasksPlus`](/mcpessentials/api-reference/Microsoft/Extensions/DependencyInjection/IMcpServerBuilder) stamps the provider on first use.

Register the store as a **singleton**. The context stays scoped. Each operation opens an `IServiceScope`, resolves `TContext`, and disposes the scope.

<Tabs>
  <Tab title="HTTP" icon="globe">
    ```csharp
    builder.Services.AddHttpContextAccessor();
    builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlServer(connectionString));

    builder.Services.AddMcpServer()
        .WithHttpTransport(o => o.Stateless = true)
        .WithTools<MyTools>()
        .WithTasksPlus<AppDbContext>(
            sp => sp.GetRequiredService<IHttpContextAccessor>().HttpContext?.User,
            o => o.DefaultTimeToLive = TimeSpan.FromMinutes(5));
    ```
  </Tab>
  <Tab title="Stdio" icon="terminal">
    ```csharp
    builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlite("Data Source=tasks.db"));
    builder.Services.AddMcpServer()
        .WithTasksPlus<AppDbContext>("local-user");
    ```
  </Tab>
  <Tab title="Store only" icon="database">
    Same factory, without `IMcpServerBuilder`:

    ```csharp
    builder.Services.AddHttpContextAccessor();
    builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlServer(connectionString));
    builder.Services.AddMcpEssentialsEntityFrameworkTasks<AppDbContext>(
        sp => sp.GetRequiredService<IHttpContextAccessor>().HttpContext?.User,
        o => o.DefaultTimeToLive = TimeSpan.FromMinutes(5));
    ```
  </Tab>
</Tabs>

## Options

Pass `Action<McpTaskStoreOptions>` as the next argument after identity.

| Knob | Default | Role |
|---|---|---|
| `DefaultTimeToLive` | `null` (unlimited) | Work window ends at `CreatedAt + TTL`. The row is discarded at `CreatedAt + 2×TTL` (`DiscardAfter`), or sooner on a terminal owner get. |
| `DefaultPollIntervalMs` | `1000` | Hint for clients. |
| `AutoSweep` | `true` | Pulse a throttled flush after create and on get. |
| `SweepInterval` | 30 seconds | Minimum time between automatic pulses. `TimeSpan.Zero` skips the throttle. |
| `ServeAndDrop` | `true` | Owner get of a terminal snapshot serves it and then deletes the row. |

```csharp
.WithTasksPlus<AppDbContext>(currentUser, o =>
{
    o.DefaultTimeToLive = TimeSpan.FromMinutes(5);
    o.AutoSweep = false;          // you own the schedule
    o.ServeAndDrop = true;
});
```

Call [`SweepExpiredAsync`](/mcpessentials/api-reference/CloudNimble/McpEssentials/Core/Tasks/IMcpTaskStorePlus) from a hosted service or SQL Agent wrapper when `AutoSweep` is off. The public handle always runs a full pass.

The EF drain is a set-delete: `DELETE WHERE DiscardAfter IS NOT NULL AND DiscardAfter <= now`. It does not load the table. SQLite stores `DiscardAfter` as UTC ticks so that comparison translates; SQL Server and PostgreSQL use the same path.

Per-row get and mutate still use `ShouldDiscard` (default `HasExpired`). Override `SweepExpiredCoreAsync` when bulk criteria must differ from the stamp.

## Events

A single instance raises `InputResponseReceived` in-process. Several nodes that wait on `ElicitAsync` need a bus: register [`IMcpTaskInputSignalBus`](/mcpessentials/api-reference/CloudNimble/McpEssentials/Core/Tasks/IMcpTaskInputSignalBus) in DI (Redis, Service Bus, …). The store publishes after a successful resolve and subscribes so the originating process wakes up.

Payload is task id plus request id. Keep tokens and elicitation secrets off the bus; the row already has the response body.

<Warning>
Missing bus plus multiple nodes means elicitation waits until timeout. That is a host misconfiguration.
</Warning>

## Isolation

`CreateTaskAsync` stamps `OwnerUserId`. Client-facing get, cancel, and resolve require that user. Another user's task is not found. Server-side complete, fail, and set-input skip the live-user check because the SDK runs those from a background DI scope after the originating HTTP request is gone.
