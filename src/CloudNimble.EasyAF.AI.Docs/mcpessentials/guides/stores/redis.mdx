`McpEssentials.Redis` is the authenticated task store for hosts that already run Redis. It subclasses [`McpTaskStoreBase`](/mcpessentials/api-reference/CloudNimble/McpEssentials/Core/Tasks/McpTaskStoreBase) and persists [`StoredMcpTask`](/mcpessentials/api-reference/CloudNimble/McpEssentials/Core/Tasks/StoredMcpTask) snapshots as JSON strings.

Prefer this over [`IDistributedCache`](/mcpessentials/guides/stores/distributed-cache) when the cache is Redis and several nodes wait on `ElicitAsync`. Redis expires keys; the request-path sweep is off by default.

The host owns [`IConnectionMultiplexer`](https://stackexchange.github.io/StackExchange.Redis/Configuration). This package ships the store and registration. Register the multiplexer as a singleton.

## Install

```bash
dotnet add package McpEssentials.Redis
```

```csharp
builder.Services.AddSingleton<IConnectionMultiplexer>(
    _ => ConnectionMultiplexer.Connect(connectionString));
```

## Wire the store

Same identity factory as [Authenticated tasks](/mcpessentials/guides/authenticated-tasks). Redis has no generic context type, so the MCP builder method is [`WithRedisTasks`](/mcpessentials/api-reference/Microsoft/Extensions/DependencyInjection/IMcpServerBuilder) rather than `WithTasksPlus<TContext>`.

```csharp
builder.Services.AddHttpContextAccessor();
builder.Services.AddSingleton<IConnectionMultiplexer>(
    _ => ConnectionMultiplexer.Connect(connectionString));

builder.Services.AddMcpServer()
    .WithHttpTransport(o => o.Stateless = true)
    .WithTools<MyTools>()
    .WithRedisTasks(
        sp => sp.GetRequiredService<IHttpContextAccessor>().HttpContext?.User,
        o =>
        {
            o.DefaultTimeToLive = TimeSpan.FromMinutes(5);
            o.KeyPrefix = "mcp";
            o.WaitReplicas = 1;
        });
```

**Stdio / single user**

```csharp
builder.Services.AddMcpServer()
    .WithRedisTasks("local-user");
```

**Store only**, without `IMcpServerBuilder`:

```csharp
builder.Services.AddMcpEssentialsRedisTasks(
    sp => sp.GetRequiredService<IHttpContextAccessor>().HttpContext?.User,
    o => o.DefaultTimeToLive = TimeSpan.FromMinutes(5));
```

## Keys and TTL

| Key / channel | Role |
|---|---|
| `{prefix}:task:{taskId}` | JSON snapshot, including `OwnerUserId` |
| `{prefix}:task:input` | Pub/sub for resolved input (`taskId` + `requestId`) |

`DiscardAfter` is stamped at write as `CreatedAt + 2×TimeToLive`. Redis `PEXPIREAT` uses that instant. Unlimited TTL (`null`) leaves the key until a terminal owner get (`ServeAndDrop`) or an explicit delete.

`AutoSweep` defaults to `false`. [`SweepExpiredAsync`](/mcpessentials/api-reference/CloudNimble/McpEssentials/Core/Tasks/IMcpTaskStorePlus) is a no-op; Redis owns expiry. Per-row get still honors `ShouldDiscard` so a custom clock can drop a key before Redis does. A custom `ShouldDiscard` that disagrees with `DiscardAfter` should also override `SweepExpiredCoreAsync` and skip native expiry.

Replica sets: set `WaitReplicas` so `CreateTaskAsync` does not return until a later get on another node can see the key. Standalone Redis leaves this at 0. Eventually-consistent Redis without wait is not SEP-2663 durable across nodes.

## Isolation

`CreateTaskAsync` stamps `OwnerUserId`. Client-facing get/cancel/resolve require that user. Server-side complete/fail/input-request skip the live-user check. Another user's task is not found. A missing key is not found; get does not distinguish expiry from isolation.

Creates use a Lua `EXISTS` then `SET`. Updates compare the expected JSON then `SET` + `PEXPIREAT`. A terminal owner get with `ServeAndDrop` (default) deletes the key after serving it.

## Events

After a successful resolve, the publishing node raises `InputResponseReceived` locally, then publishes JSON `{ taskId, requestId }` on `{prefix}:task:input`. Other nodes subscribe and raise a stub response so `ElicitAsync` waiters wake. The publisher drops its own pub/sub echo.

See [Stores](/mcpessentials/guides/stores).
